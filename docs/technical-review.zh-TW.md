## 虎牙播放

原本直接嵌入 `www.huya.com` 的完整直播間。實測時頁首及賽事資訊占據大部分窗格，播放器被擠到下方，且曾觀察到播放時間幾乎停止推進。現在將直播間路由到[虎牙站外播放器](https://liveshare.huya.com/iframe/660000)：

| 輸入 | 實際載入 |
| --- | --- |
| `https://www.huya.com/660000` | `https://liveshare.huya.com/iframe/660000` |
| `https://m.huya.com/lpl` | `https://liveshare.huya.com/iframe/lpl` |

房號與別名格式已對照虎牙的[播放器前端程式](https://hd.huya.com/h5/livesharePc/js/app.cdbc3c22.js)。首頁、分類、影片、活動及既有站外播放器網址保留原樣。

改善後以 Chrome for Testing 148.0.7778.96 載入實際擴充套件，四窗格中同時測試上述兩個來源。兩個來源均取得 1280 × 720 影片，播放時間與解碼影格持續增加；調整分隔線及切換語言保留原 iframe。觀察期間一個來源曾進入緩衝，設定狀態也正確顯示為緩衝中，而另一個來源繼續播放。

尚未取得使用者原先失敗的房間網址，因此上述結果僅代表測試來源與環境。虎牙服務、登入、地區、是否開台與自動播放政策仍會影響實際播放；沒有加入無限自動重試或第三方解析服務。

使用者後續截圖顯示右側被裁切的是虎牙彈幕設定選單。官方播放器使用 210 × 220px 選單與負的左側位移，當彈幕按鈕靠近窗格右緣時會越界。現在將彈幕及畫質選單固定在播放器視窗內；彈幕選單依可用寬高等比例縮小，畫質選單限制高度並可捲動。沒有修改影片寬高、`object-fit` 或裁切影片內容。

「進入直播間」中央提示與控制列按鈕由精確的元素選擇器隱藏，播放器動態重建後仍有效。輔助程式僅匹配 `liveshare.huya.com/iframe/*`，且驗證是本套件直接嵌入；一般虎牙分頁保留原貌。

以真實虎牙 `660000` 直播驗證：559px 寬窗格中，隱藏進房按鈕後，原彈幕選單右緣到達 635px；修正後右緣為 551px。加寬畫質選單也在窗格內，彈幕透明度選項可實際點擊。切換 2／3／4 窗格並縮小至 201 × 161px，彈幕選單完整可見，影片仍為 1280 × 720；觀察期間播放時間由 0.91 秒增至 4.25 秒，解碼影格由 30 增至 130。

## Twitch 載入調查（2026-09-18）

1.2.0 原本只有 Twitch 平台標籤辨識，`https://www.twitch.tv/roger9527` 仍載入完整直播間，連同導覽、推薦、聊天室及頻道資訊一起初始化。改為使用 [Twitch 官方播放器](https://dev.twitch.tv/docs/embed/video-and-clips/)，`parent` 取目前 dashboard 的 hostname，搭配既有僅限版面分頁的 iframe 回應標頭規則。只轉換桌面／手機的直播頻道網址；VOD、剪輯、分類及既有播放器網址保留原樣。

播放器要求靜音自動播放，明確指定的 `autoplay=false`／`muted=false` 則保留。實測 Twitch 仍可能等待使用者點擊播放，不能把停在播放按鈕的畫面當成持續載入。原本播放狀態只在初始化、媒體事件及 dashboard 查詢時回報；若頁面較晚插入尚無影片來源的 paused video，就可能一直顯示「尚未確認播放」。現在針對新增／移除節點中的 video 排程狀態更新，合併 250ms 內的變動，隱藏分頁時停止 DOM 觀察；一般聊天室文字變動不會觸發影片狀態掃描。

以 Chrome for Testing 148.0.7778.96 與獨立測試設定檔載入真實擴充套件及羅傑直播。原本完整頁面在 20 秒觀察窗內發出 303 次 script 請求；修改後從原頻道網址進入官方播放器，25 秒觀察窗內為 118 次。這是單次資源請求觀察，並非載入時間或 CPU 效能基準。修改後第 5 秒已顯示「已暫停」，點擊播放後取得 1920px 寬影片，播放時間從 4.78 秒持續增加至 9.78 秒，設定面板同步顯示「播放中」。未重現使用者環境的長時間黑畫面，因此不能排除其網路、登入狀態或其他擴充套件的影響。

新增路由與延後建立／替換／移除影片的回歸檢查；64 項離線測試與完整瀏覽器整合測試通過。

後續使用者仍回報 Twitch 整片灰色。iframe 即使被瀏覽器封鎖也可能觸發 `load`，原本此時就取消逾時計時，會永久停在「頁面已載入」。現在 Twitch 嵌入必須回報實際影片狀態才取消初始化期限；20 秒內未確認影片或出現媒體錯誤，僅重載官方嵌入播放器一次，之後顯示錯誤或尚未確認播放，不再切換完整直播間。已建立但暫停等待點擊的影片會取消逾時，不會被自動重載。以瀏覽器攔截模擬 `blockedbyclient` 及成功回應但無播放器的空白頁，均驗證只重試嵌入播放器，媒體錯誤也不會改載完整網頁。這是失敗恢復機制，尚未取得使用者瀏覽器中的確切封鎖原因。2026-09-20 以 Chrome for Testing 153 再測 `roger9527`，點擊嵌入播放器的 Play 後為 1920 × 1080，五次間隔五秒的觀察中播放時間由 4.47 秒增至 24.52 秒，來源維持 `player.twitch.tv`。

## 早期 Kick HLS 串流試驗（2026-09-20）

Kick 頻道網址改為查詢 `api/v2/channels/<channel>` 的 `playback_url`，由 `<video controls>` 顯示 Chrome 控制列。播放器右上方提供「更新直播來源」及自動／手動畫質選單；Kick 的設定面板不再提供單格重整按鈕。控制列在滑鼠操作或鍵盤聚焦時顯示，閒置 2.2 秒或游標離開後隱藏；操作控制列時維持可見。每格最多一個閒置計時器，重整／移除時取消計時及事件監聽。每次更新重新查詢 API，保留頻道網址與畫質偏好，不持久保存帶簽章的 m3u8。離線或查詢失敗時，播放器內仍保留可重試的更新按鈕。

本地 HLS.js 1.7.3 在首次載入 Kick 時才載入，使用套件內的 worker。自動畫質參考頻寬、窗格尺寸及掉幀；手動畫質以解析度／幀率儲存，更新後若無該畫質則回到自動。使用 `loadLevel` 改變後續下載，保留既有緩衝，故畫質變更可能延後生效。直播預留四段距離、關閉低延遲模式，以增加延遲換取穩定性；播放清單若宣告六秒 TARGETDURATION，目標直播距離約為 24 秒，實際每段長度可能較短。

前向緩衝目標 30 秒、上限設定 60 秒、保留 15 秒後向緩衝；`maxBufferSize` 設為 30 MB，但這不是整個分頁或解碼器的硬性記憶體上限。HLS 引擎內部重試後，額外網路與解碼恢復各最多兩次。換來源、更新及移除窗格會中止舊查詢、取消重試、銷毀 HLS 引擎並清除 video 來源；不啟動持續掃描整頁的計時器。

以 Linux Chrome for Testing 153.0.8010.52 實測兩路 `starladder`：30 秒觀察沒有新增 `waiting` 事件，播放到 720p60；手動切換 360p30、1080p60 均確認實際影片尺寸改變。連續更新六次保留另一播放器及 720p60 偏好，worker 數維持一個，清空來源後為零。垃圾回收後的主頁 JavaScript heap 約由 4.85 MB 變成 4.99 MB；這是短期觀察，並未涵蓋瀏覽器總記憶體、媒體解碼緩衝或長期使用。另確認延後載入 HLS、180px 窄窗格控制列與清理正常。109 項離線測試及完整瀏覽器整合測試通過。

## 導入前的 IVS 引擎試驗（2026-09-20）

使用獨立的 MV3 測試擴充功能、本地 Amazon IVS Player SDK 1.56.1、Linux Chrome for Testing 153.0.8010.52，以及 Kick `starladder` 的當前串流，與正式程式的 HLS.js 設定同時播放。此階段僅進行測試、尚未替換 HLS.js；後續正式導入見下一節。整個過程沒有加入 AWS 帳號、憑證或建立雲端直播資源。

第一輪 60 秒觀察中，IVS 的 `getLiveLatency()` 為 1.47～1.78 秒；HLS.js 的 `latency` 約 24.1 秒。兩者開始播放後都沒有新增 `waiting` 事件。這是各引擎回報的直播距離，定義並不完全相同，也不是攝影機到螢幕的端到端量測。IVS 自動選到 1080p60，HLS.js 因窗格尺寸選到 480p，因此不能據此比較兩者的 CPU／掉幀優劣。短期測試也不能保證網路波動下永不卡頓。

原生 `<video controls>` 與 IVS 手動畫質有相容限制：保留 Chrome 控制列時，呼叫 `setQuality(360p)` 後等候 20 秒仍為 1080p；[SDK 文件](https://aws.github.io/amazon-ivs-player-docs/1.56.1/web/interfaces/Player.html#setQuality)明載 `controls` 存在時，這個 API 不生效。這不符合目前同時需要原生控制列與手動畫質的介面需求。關閉測試頁的原生控制列後，360p 與 1080p60 均能成功切換，證實限制與 `controls` 有關。

資源清理測試中，先播放一個 IVS，再連續四次呼叫 `delete()` 並建立新播放器。每次重建增加一個 WASM worker；刪除最後的播放器後，再等候 20 秒，仍有五個 IVS worker，HLS.js worker 則已清除。垃圾回收後的主頁 JavaScript heap 約由 4.83 MB 增為 5.19 MB，但不包含 worker／WASM 記憶體，不能用此推論總記憶體已回收。這是此版本與測試環境的觀察，尚未據此宣稱所有環境均有洩漏；正式導入前需要解決生命週期清理及控制列相容問題，因此本次未替換正式引擎。

測試擴充功能以同源 worker／WASM 檔案載入，需在其 CSP 的 `script-src` 加入 `'wasm-unsafe-eval'`；直接把文件範例的 `worker-src blob:` 用於 MV3 擴充頁會導致載入失敗，同源 `worker-src 'self'` 可正常運作。正式 manifest 沒有套用試驗用的 CSP 變更。

本次播放既有 Kick 串流不會建立使用者的 AWS 計費資源。[Amazon IVS 計費](https://aws.amazon.com/ivs/pricing/)以服務帳號的直播輸入與觀眾輸出用量等項目計算；若將來自行建立 AWS IVS 頻道，才需要另估服務費，不能把整項直播服務視為免費。

## 正式導入 IVS、自製控制列與 LIVE（2026-09-20）

Kick 現在使用本地 Amazon IVS Player 1.56.1，每個窗格由獨立的擴充頁面 `kick-player.html` 承載引擎及控制列；dashboard 本身不載入 SDK。停用原生 video controls，提供播放／暫停、靜音、音量、LIVE、自動／手動畫質與全螢幕。控制列閒置 2.2 秒後隱藏，支援鍵盤操作及 180px 窄窗格；Space/K 播放／暫停、M 靜音、F 全螢幕、L 回到直播。

LIVE 取代「更新來源」按鈕，重新取得目前直播來源，以同一個 IVS 實例接回最新直播位置，保留畫質及音量。暫停後恢復播放也走 LIVE，明確覆寫網址的 `autoplay=false`，因為這是使用者主動播放。低延遲模式與 `setRebufferToLive(true)` 開啟，SDK 在緩衝中斷後優先接回直播。這不是 DVR，不承諾保留暫停期間內容，也不代表完全零延遲。

畫質由目前串流提供，以解析度與幀率儲存偏好；不存在的畫質回到 Auto。Auto 使用 IVS 自適應能力，並由 ResizeObserver 更新窗格尺寸上限；手動選擇以平順切換模式套用。SDK／worker／WASM 全部包在擴充功能中，CSP 只新增本地 WebAssembly 所需的 `wasm-unsafe-eval`，worker 限同源，不允許遠端 JavaScript。

一般 LIVE 重用實例；更換來源、移除窗格、離線查詢及錯誤後重新建立時，銷毀播放器並移除其 iframe，確保整個 worker 環境一併結束。查詢仍有八秒上限及取消／過期回應保護。程式不新增無限重試、持續查詢 Kick API 或掃描頁面的計時器。

真實 Chrome 153 雙窗格 `starladder` 測試：初始 30 秒沒有新增 waiting，延遲讀值 1.70～2.09 秒；手動 360p30、1080p60 均確認 video 實際尺寸改變。回到 Auto 時觀察到一次短暫 waiting，不能保證所有切換都不中斷。連按 LIVE 五次，worker 維持兩個；移除一格後為一個，再重複新增／移除三次仍維持一個；清空所有來源後為零，另一格在測試期間保留原 iframe。垃圾回收後主頁 JS heap 從雙播放器時的約 5.42 MB 降至清空後的 2.54 MB，這不包含完整瀏覽器、worker／WASM 及解碼器記憶體，也不是長期穩定性保證。

108 項離線測試及完整瀏覽器整合測試驗證實例重用、畫質、播放偏好、LIVE 與暫停後回直播、音量、全螢幕、過期回應、離線恢復、查詢新來源途中舊引擎出錯的清理、換位與窄窗格介面。另以真實直播確認暫停後回到 LIVE 仍保留 720p60、25% 音量與取消靜音，恢復後延遲讀值約 1.82 秒。瀏覽器回歸使用 canvas 串流 fixture，真實直播另行測試。

## 本地直播播放器自動恢復（2026-09-21）

Twitch／Kick 每個窗格由 `src/live-recovery.js` 管理自己的恢復狀態，狀態不隨播放器 iframe 重建而歸零。暫時性解析錯誤、SDK 播放錯誤／結束，以及前景播放時間或解碼影格持續 20 秒沒有進展，會重新解析來源並替換播放器頁面。音量／靜音在 SDK 銷毀前保存，畫質沿用窗格偏好；只重建發生問題的窗格，不重新載入其他來源。

自動重試依序等待 2／5／10 秒，最多三次；連續 60 秒有播放進展才恢復額度。短暫收到 PLAYING 或重建 iframe 不會重設次數。達到上限顯示「自動恢復已停止」，可按 LIVE 手動重新開始。來源解析明確回報離線、401／403、Twitch integrity／授權拒絕，以及 SDK 不支援的功能不自動重試。播放中的授權錯誤則先重取來源，以便更新失效網址；若新來源仍拒絕授權就停止。429 至少等待 30 秒，Twitch 的 429／503 也會採用 Retry-After（上限五分鐘）。

手動暫停與 autoplay=false／瀏覽器阻擋自動播放不觸發監控。隱藏分頁與長時間計時器延誤會重設觀察起點，避免將背景停止渲染、電腦睡眠視為卡死。偵測到斷網後等待恢復，不消耗重試額度；重新連線再取新來源。窗格交換保留控制器，更換來源、縮減版面或清空窗格會取消控制器與解析請求，舊回應不能覆蓋新來源。

SDK 錯誤保留經篩選的類型、數值代碼與來源元件，區分授權、網路及媒體錯誤；原始錯誤字串可能包含簽章網址，因此不保留。這次新增的模擬時鐘測試涵蓋退避、停止條件、斷網、背景／睡眠、影格凍結、額度恢復及取消。瀏覽器回歸另外使用實際 MV3 頁面與 canvas SDK 替身驗證重建、來源更新、設定保留及窗格隔離。真實廣告轉場與跨 token 期限的長時間觀看仍需另行實測；此機制不會生成 Client-Integrity 或跳過平台授權。

## 自製播放器效能檢查（2026-09-21）

確認並改善三項不必要的操作：

- 分隔線拖曳會透過 ResizeObserver，幾乎每個畫面更新都呼叫 `setAutoMaxVideoSize()`；目前 SDK 每次呼叫都會傳訊息給 WASM worker。現在合併 250 ms 內的尺寸變化，略過相同整數尺寸；首次設定及新來源 READY 時立即套用最新上限，移除播放器時取消待處理更新。ResizeObserver 直接使用回報的尺寸，避免再讀取元素尺寸。手動畫質選擇不受影響。
- 原本同時使用 `setAutoplay(true)` 與 READY 時呼叫 `play()`。依 [IVS 1.56.1 API 文件](https://aws.github.io/amazon-ivs-player-docs/1.56.1/web/interfaces/Player.html#play)，啟用 autoplay 後不需要再次呼叫 play；現在只由 SDK 自動播放，保留明確停用 autoplay 的行為。
- 每次 pointermove 都對控制列重複加入相同 class。現在只有從隱藏轉為顯示時更新 class；後續活動只延長既有的隱藏期限。

新增離線回歸以每 16 ms 改變尺寸一次、連續 120 次的情境重現問題：包含初始尺寸的 SDK 更新由 121 次降至最多 9 次，且最後尺寸正確。另驗證重複尺寸、新串流重新套用、手動畫質及銷毀後取消更新。瀏覽器回歸使用真實 ResizeObserver 與 canvas SDK fixture，檢查連續縮放的呼叫上限、120 次 pointermove 僅產生一次 class 變更，以及每次載入只啟動一次播放。

155 項離線測試與完整瀏覽器回歸通過；本次瀏覽器執行中，60 次逐畫面縮放合併為 4 次 SDK 尺寸更新。另以正式 SDK、真實 Twitch `roger9527` 雙窗格驗證：30 秒播放時間及影格持續增加，沒有新增 waiting；手動畫質／Auto、暫停恢復、三次 LIVE、音量保留、全螢幕及停用 autoplay 均通過，移除窗格後 worker 依序為 2 → 1 → 0。

這些數字衡量的是引擎呼叫與 DOM 更新次數，不能換算為整體 CPU 或記憶體節省比例。原本已有單一引擎重用、移除 iframe 以釋放 worker、有限次數斷線恢復；本次保留這些行為。多路高解析度串流的解碼成本，以及長時間實播的 CPU／GPU／完整記憶體用量，仍需在實際裝置量測。

## Bilibili 來源標題（2026-09-18）

官方嵌入播放器的 `document.title` 固定為 `Bilibili Live Activity Player`，並非直播間標題。解析房號並建立播放器後，現在另外以 `room/v1/Room/get_info?room_id=實際房號` 在背景取得 `data.title`，且忽略播放器回報的通用名稱與空標題。標題查詢最多等待 8 秒，失敗時保留已知標題或顯示 `Bilibili · 房號`，不阻塞播放或把來源標記為失敗；重新載入來源會重新查詢。

回應綁定原 iframe，套用時檢查它仍在頁面中及來源網址仍相符，並重新讀取交換後的窗格位置；重新載入同一網址時，舊 iframe 的遲到回應也會被忽略。實際擴充套件驗證房間 6 顯示「【直播】WE vs JDG」、35 顯示「SL群星联赛秋季赛」，播放器均已完成載入且存在 video，重新開啟設定後標題仍正確。67 項離線測試及完整瀏覽器整合測試通過。

## 實作要點

- 網路規則更新排入同一個佇列，避免較慢的更新覆蓋較新的分頁狀態。只接受本套件 dashboard 主框架的安裝請求；空分頁清單會刪除規則，不會建立全域規則。規則錯誤會傳回介面。這些規則使用 Chrome 的 [session rules](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest) 與[分頁事件](https://developer.chrome.com/docs/extensions/reference/api/tabs)。
- 載入工作綁定窗格元素，換網址、關閉窗格或重試時使舊工作失效；未更動的 iframe 持續重用。重試一個來源不會套用其他來源尚未套用的網址。
- 狀態與重試按鈕集中在設定對話框。iframe 的載入完成不等於影片正在播放；只有來源內的可見 HTML video 狀態可確認播放，其他頁面顯示「頁面已載入・尚未確認播放」。巢狀 iframe 或自訂播放器可能只能取得頁面狀態。
- 大範圍 DOM 探索限制為 30 秒，期間合併密集變動。找到播放器後縮小觀察範圍；仍保留低頻檢查，以支援稍後才出現或被替換的播放器。尚未量測 CPU／記憶體節省比例。
- 延續原生 JavaScript 與 MV3 架構，不引入前端框架；Kick 需要時才載入本地播放器程式庫。
- 草稿與清除復原保留在目前分頁記憶體中；關閉設定對話框仍保留，重新整理或關閉分頁後消失。切換版面只載入已套用來源，收合的來源仍可展開編輯。清除復原不會還原其間變更的語言與版面；復原來源會重新載入播放器。
- 緊湊面板在同一組繁體中文測試來源下，雙來源高度由約 627px 降至 448px，四來源由約 914px 降至 649px，約減少 29%。1366 × 768 視窗下，四來源加上待套用提示可完整顯示；較矮視窗仍可捲動，套用按鈕固定可見。數值會隨語言與錯誤訊息換行而變動。
- 排序時已套用來源與其草稿一起移動，可見窗格之間交換仍沿用原 iframe。收合卡片即使有瀏覽器回報的尺寸，也不會成為拖曳目標或 Tab 焦點。

## 驗證

108 項離線測試涵蓋來源路由（含 Twitch、Kick、SOOP 頻道、保留頁面、parent 與播放參數）、Bilibili 標題查詢及回應驗證、網址容錯、API 逾時與重試、規則生命週期／權限檢查／非同步順序，以及播放器觀察的範圍、節流、截止與恢復行為。

瀏覽器整合測試以本地回應內容與 canvas 影片，驗證以下情境，無需外部直播服務：

1. 慢速來源不阻塞另一窗格。
2. 過期回應不覆蓋新網址，待解析來源在交換位置後載入正確窗格。
3. 單格重試保留其他 iframe 及未套用的輸入。
4. 真實 HTML video 播放／暫停事件經由 content script 回報至版面。
5. 實際 8 秒逾時只讓該來源顯示錯誤。
6. 不完整網址、對話框焦點循環、Escape 與鍵盤分隔線。
7. 規則安裝失敗可見，重試後消除提示。
8. 真實擴充套件中兩個版面共存，導向外頁、關閉分頁後清理規則。
9. YouTube 嵌入失敗切換至完整頁面，播放器被替換後重新套用版面，以及 YesLive 播放器擷取。

## 後續可選方向

- 一般直接貼上的 `.m3u8`／`.mpd` 仍交給 iframe／瀏覽器處理；後續可考慮將 Kick 的 HLS 控制擴充到其他來源，並另行驗證 CORS、codec 與 DRM。
- 隨平台數量增加，可將純來源解析邏輯抽出獨立模組；目前優先穩定既有輕量架構。
- 建立四路長時間播放的 CPU、記憶體與斷線恢復基準，量測後再決定是否需要更多節流或背景暫停策略。

## 套用更新

到 `chrome://extensions` 重新載入套件，再重新整理已開啟的 Stream Layout 分頁。原本的來源網址與版面設定可以沿用。若某個來源失敗，打開設定對話框，使用該來源的「重試」。
